Reported as "key based transpose is glitching", "glitching except on certain pitches and tones", and "its not pitch locking the keys". Root cause found 2026-09-06 and it was NOT the transpose engine. Rule out the engine first: build test-audio-corpus/multitranspose_harness.cpp locally (g++ -std=c++17 -O2 -D_USE_MATH_DEFINES -I effects/home/faust, the _USE_MATH_DEFINES is required on MinGW or vowelFormant.h fails on M_PI) and sweep pitch x shift. It tracked the commanded ratio within 17 cents across 60 cases with zero failures, which proves the fault is in WHICH ratio gets commanded, not in the shifter. The bug: multitranspose.dsp only trusts the external autocorrelation tracker when extFreqDetApplies holds, and that carried an extra term freeDiagRaw < 0.5. audio_thread.cpp filled freeXposeBuf straight from monitorFoldVal, i.e. from whether SHIFT is physically held -- and engaging MultiKey mode is itself a SHIFT gesture. So in ordinary use the guard was false, pitchtracker.lv2 was bypassed, and freqDet fell through to the internal zero-crossing tracker documented as taking well over 400ms to converge and drifting non-monotonically. Its accuracy is pitch-dependent, which is exactly why the glitching happened on some pitches and tones and not others. Why the guard was wrong: its intent was that in free mode the DSP analyses loopSum while the tracker analyses live input, so the reading would not match what is shifted. But the fold at the top of the audio block already crossfades fin toward prevLoopSum by foldGain, and the tracker copies fin AFTER that fold, so it was analysing the correct blended signal all along. The real inconsistency was that freeXpose used the raw button state while the audio fold used foldGain, which is deliberately forced to zero when a transpose voice is gated (holding SHIFT and playing a key must not fold). So the DSP switched its analysis source to loopSum in exactly the case where the audio path did not. Fix: freeXpose follows foldGain, and the redundant freeDiagRaw guard is removed. foldGain had to be hoisted above both uses; it is static so the earlier read sees the previous block, which matches the fold relationship already in place. General lesson: when a signal-path guard references a mode flag, verify the flag is derived from the same quantity the audio path actually uses, not from the raw control that nominally sets it. A guard that was correct when written can be silently invalidated by a later change to what the audio path does.
