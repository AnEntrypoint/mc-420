Reported as: changed the tempo, no pitch change on the playing loops. Fixed 2026-09-06. Two causes. ONE, the main one: linkSpeedRatio in audio_thread.cpp was gated on !linkSnap.weOwnTempo. proposeTempo sets g_weSetTempo true at the moment the FIRST loop finishes recording, and resetTempoAuthority is only called on erase or clear-all, so after recording anything that flag stays true for the whole session and the varispeed was permanently disabled. AGENTS.md documents weOwnTempo as guarding proposeTempo -- stopping us rewriting the session tempo out from under other peers -- so using it to gate playback varispeed conflated two unrelated concerns. If a peer moves the tempo we must follow it whoever set it originally. Gate removed from the ratio, left in place on proposeTempo. TWO, a regression from the immediately preceding commit in the same session: the phase trim ran whenever Link drove the length, including while linkSpeedRatio was still 1.0 because no recorded_bpm existed. With the ratio at 1.0 the master phase can never track the Link grid, so the phase error grows without bound and the trim saturates at its clamp. Live telemetry showed eff_speed 0.9700 with nothing playing at all -- a permanent 3 percent (51 cent) detune. The trim now runs only while linkVarispeedEngaged, and is cleared otherwise. How to check this quickly without recording anything: read /run/aloop/status.json. eff_speed must be exactly 1.0000 when no loop is recorded, whatever Link is doing. If it sits at 0.97 or 1.03 with nothing playing, the trim is saturating and the ratio is not engaged. Note recorded_bpm is only written when the first loop FINISHES recording (ApcGrid, deriveTempoQuant on the take length), so before any take the ratio is legitimately 1.0 and that is not the bug.
