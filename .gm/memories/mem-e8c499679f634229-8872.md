multitranspose.dsp (key-lock polyphonic pitch engine) investigation history, drained from AGENTS.md during compaction.

SHIFT/free-guard mechanism history: reported as 'key based transpose is glitching', 'glitching except on certain pitches and tones', 'its not pitch locking the keys'. The transpose engine itself was ruled out via the standalone harness (test-audio-corpus/multitranspose_harness.cpp, g++ -std=c++17 -O2 -D_USE_MATH_DEFINES -I effects/home/faust -- _USE_MATH_DEFINES required on MinGW or vowelFormant.h fails on M_PI): tracked commanded ratio within 17 cents across 60 cases (6 fundamentals x pure/harmonic x 5 shifts), zero failures. The actual cause was WHICH ratio got commanded: extFreqDetApplies carried an extra term freeDiagRaw<0.5, and audio_thread.cpp filled freeXposeBuf straight from monitorFoldVal (whether SHIFT is PHYSICALLY HELD). Engaging MultiKey mode is itself a SHIFT gesture, so in ordinary use that guard was false, pitchtracker.lv2 was bypassed, and freqDet fell through to the internal zero-crossing tracker (pitch-dependent accuracy, explaining why glitching appeared on some pitches/tones and not others). The guard's original intent was defensible (in free mode the DSP analyses loopSum while the tracker analyses live input) but had stopped matching reality: the fold at the top of the audio block already crossfades fin toward prevLoopSum by foldGain, and the tracker copies fin AFTER that fold, so it had been analysing the correct blended signal all along. The real inconsistency: freeXpose used the raw button state while the audio fold used foldGain (deliberately forced to zero when a transpose voice is gated). Current behavior: freeXpose follows foldGain, the redundant guard is gone, foldGain is hoisted above both uses as static so the earlier read sees the previous block. Transferable rule: when a signal-path guard tests a mode flag, verify that flag is derived from the SAME quantity the audio path actually uses, not the raw control that nominally sets it -- a guard correct when written is silently invalidated by any later change to what the audio path does.

A separate, since-reverted attempt (shiftAmount latching at attackEdge instead of continuous re-tracking, plus a trackingAllowed change) was built and shipped based on a real discrepancy (AGENTS.md's own prose said shiftAmount was 'sampled once per voice at attackEdge, held for the whole sustain' but the code glided toward shiftTarget every sample) then reverted when the user reported the lock was still not working -- the SHIFT/free-guard mechanism above was the actual cause. The lesson: this file's prose was right and the code had drifted from it, exactly the failure the project's 'never trust an in-repo comment as ground truth' rule warns about -- reading the code against its own spec is what found the discrepancy.

Residual degradation analysis: corpus degradation ratio settles ~2.21 at +12 semitones after the splice crossfade change; measured three ways to confirm this is NOT engine-added distortion: (1) spurious energy on a pure tone is -64 to -67dB at every shift, no worse at shift than unity; (2) roughness is no longer splice-localized (windows inside vs between splices: ratio 1.00-1.01 at 110/196/440Hz, vs before where splices WERE the defect); (3) clicks are gone, 0/112 synthetic cases. Conclusion: the residual is PSOLA legitimately restructuring harmonically rich material (splicing every period changes short-window second derivative), not an artifact. Two sharper metrics were tried and refuted: off-harmonic-grid energy flagged piano_mid_C4 at +9.6dB but was measuring the piano's own 3-unison-string beating (257.8/260.7/263.7/266.6Hz), not a defect; envelope-deviation-from-ideal-shift reports 12-15dB rms on every file because PSOLA deliberately preserves the formant envelope, so that metric penalizes the engine's own intended behavior.

pitchtracker.lv2 accuracy measurement: driven through DawDreamer's Faust JIT (pitchtracker_ac.dsp declares no ffunction so the JIT limitation doesn't apply to it, unlike multitranspose.dsp) against all 16 real instrument recordings, cross-checked against FFT harmonic-comb score: accurate within 50 cents on 9 files (66-706Hz), genuinely wrong on 3 files (all >=500Hz: oboe_mid_C5B5 reads 262.9Hz vs true 527Hz, an octave-down subharmonic lock, comb score 296.9 for 527 vs 214.9 for 263; violin_high_sulE_C7E7 reads 436.4Hz vs ~1035Hz, comb score 9.6 vs 173, not even a subharmonic; trumpet_high_C6 at -63.9 cents), 4 reference/range artefacts (piano_low_A1 correctly returns 0, f0~55Hz below the 60Hz minTrackHz floor). subharmonicPromote exists for exactly the oboe case and structurally cannot catch it: it requires c2>cCoarse+subharmDominanceMargin, but at a TRUE subharmonic lag the normalized autocorrelation is genuinely higher than at the fundamental on a periodic signal, so the test can never fire for the octave-down case it targets; subharmDominanceMargin is only 0.004, widening it is not the answer. Below 500Hz (everything this pitch-lock is actually played with: guitar/bass/vocal) the tracker is accurate everywhere measured: -3.7c bassoon, -6.1c cello, -6.6c violin low, +6.3c trumpet low, -12.7c piano mid, -2.5c marimba mid, -3.6c vibraphone, +6.6c piano high, +22.9c vocal. Deliberately left as-is -- pitchtracker_ac.dsp is on the wrong side of the project's compile-time-cliff (a multi-GB codegen blowup from one attempted per-candidate-tau-selection change), re-opening needs a real measured win justifying that risk.

Splice path upward-shift mechanism history (supersedes an earlier 'splice path is mysteriously inaccurate' note): triggerSpliceByPeriod fired only on driftFromTarget>trigger (reader falling behind, what a downward shift produces). On any upward shift the reader gains on the writer, drift goes negative, periodic resplice could never fire; the only remaining path (emergency branch at gap<SINC_HALF+2) was effectively a no-op since newPos=wr-64 sits within half a period of the reader, so period-multiple rounding gave 0 and both crossfaded readers landed on the same position -- the reader then overran the writer and read ring-stale audio, measured as -200 cents. Root cause behind that: INITIAL_READ_OFFSET_DEFAULT is 64 samples but one period at 110Hz is 436 -- no headroom behind the writer to resplice backward into. Current mechanism: upshiftTargetLag() raises the target lag to kUpshiftLagPeriods(1.5)*period+SINC_HALF+2 whenever m_scale>1.0, and the drift test is symmetric (driftFromTarget<-trigger jumps the passive reader backward by n*per through the same value+slope candidate search -- textbook SOLA for pitch-up). shrinkSpliceCount bounds |n| on both sides. Measured on a clean sine (splice path isolated, mixTgt forced to 0), before/after: worst upward error -204.7c to +18.9c, envelope-stability cv 0.46 to 0.044, amplitude drops 15 to 0. Downward/unity bit-identical across a 180-case sweep -- mono engine provably untouched. The scale>1.02 forced-grain override (which existed purely to paper over this) is gone since the splice path now beats the grain path on envelope stability at neutral formant.

Historical, now superseded -- GrainFormant is entirely inert on the poly/multitranspose path (pitch_poly_ffi.h no longer calls eng.setFormantDepth() at all; verified max grain mix 0.000000000 across formant -1.5..+1.5), since formants moved to the LPC spectral-envelope shifter. These findings describe behavior of a mechanism that no longer runs here (still relevant to the MONO pedal-ride engine, which still calls setFormantDepth via pitch_ffi.h): (1) GrainFormant shifted pitch by an exact octave (+1193 cents) at formant depth>=0.9 -- structural cause: the grain window is 2*Tin long while its read span is len*fm, so at fm~2 each grain carries ~4 input periods compressed into 2 output periods and the resampled periodicity dominates the OLA hop meant to set pitch; shortening the window would make it shorter than the hop and open gaps (the tension IS the 'gappy' artifact on the grain path). (2) GrainFormant's epoch free-runs by Tin rather than locking to real pitch marks (m_inEpoch+=Tin, refreshed only on ~43ms SNAC hops via a period/8+2 slew clamp) causing amplitude modulation when Tin is stale -- measured clean at <=0.6% modulation depth with an exact period, degrading to 2.6-4.9% with 1-8% period error or 3%/5Hz vibrato; a secondary contributor (~0.6dB) vs the upward-shift mechanism's order-of-magnitude-larger effect (envelope cv 0.46, 15 amplitude drops); real pitch-mark locking was never implemented. (3) Reducing the grain path's targetLag (Tin*(3+fm), 40-60ms at low guitar notes) was tried and made envelope stability monotonically worse (mean cv 0.0231 shipped, 0.0347 at a 960-sample ceiling, 0.0515 at periods=1.0) -- latency there is not free quality, shipped constants retained.
