image/serve-netboot-win.js -- durable facts from stripped comments not already in AGENTS.md's netboot sections: (1) GitHub's artifact-download endpoint answers with a 303 (not 301/302) redirect to a pre-signed Azure Blob Storage URL (SAS token in the query string). WITNESSED: forwarding the GitHub 'Authorization: token ...' header onto that redirect target makes Azure return 403 (it rejects an auth header it doesn't recognize on a URL already authorized via its own signature) -- the Authorization header must be stripped once the redirect leaves api.github.com, sent only to the original host. (2) Windows commonly has THREE different bash.exe on PATH (Git-Bash which understands native C:/... paths, the WSL launcher stub under System32, and a WindowsApps alias); a plain execFileSync('bash', ...) resolves whichever PATH lists first for the current process, and WITNESSED live resolved to the WSL stub which cannot see C:/dev/... at all ('No such file or directory' on a path that verifiably exists) -- pin the real Git-Bash install path explicitly rather than relying on PATH order. (3) A SYNCHRONOUS execFileSync rebuild call freezes the entire Node event loop for as long as it runs (no more DHCP/TFTP/HTTP serving, no checkAndUpdate ticks) with no timeout, so a genuinely stuck child subprocess freezes the server indefinitely with zero log output; the fix is running the rebuild ASYNC (execFile, awaited) with an explicit timeout so a stuck child is killed and the catch logs+retries next tick. (4) WITNESSED live: an update-in-progress guard wedged and the server then answered TFTP/HTTP with a STALE netboot root for 19+ hours while logging nothing but 'rebuild already in progress' -- a freshly written SD card looked like a broken fix because the Pi netbooted the stale served image instead of the SD card; the guard must be time-bounded (held far past any legitimate rebuild duration means it's wedged and must recover loudly) since a subprocess-level timeout alone cannot save you from the surrounding async flow itself hanging (a suspended promise/await). (5) Verify the rebuild actually replaced the served payload (compare the served apkovl the Pi will fetch against the binary just laid in) before recording the build as current -- a real incident had the served root silently stay on an old build while the updater believed it was current, a subtler failure than a simple stale-SHA comparison catches.
