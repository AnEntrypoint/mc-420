image/serve-netboot.sh is a Linux/WSL-host companion to src/net/config/netboot-dnsmasq.conf (the project's Windows-native path is image/serve-netboot-win.js, documented in AGENTS.md; this Linux path is NOT currently documented there). WITNESSED working on a real Pi 4 (serial 7bec0617) over a WSL2/ICS link. Usage: sudo image/serve-netboot.sh [--iface eth0] [--root /srv/tftp/aloop-netboot] [--server 192.168.137.1] [--net 192.168.137.0] [--proxy], run as root on a Linux/WSL host on the same L2 as the Pi. --iface = interface cabled to the Pi (default eth0), --root = the netboot root built by build-netboot.sh (default /srv/tftp/aloop-netboot), --server = this host's IP on that link (default 192.168.137.1), --net = the LAN network (default 192.168.137.0), --proxy = proxy DHCP instead of standalone (use when another real DHCP server already leases to the Pi; standalone is the default/witnessed-working mode for a Windows-ICS link that does NOT lease to the Pi). The netboot root must have been built with a MATCHING NETBOOT_SERVER so the baked cmdline.txt HTTP URLs point back here: NETBOOT_SERVER=<--server> image/build-netboot.sh. Three pieces, each required: (1) dnsmasq DHCP hands the Pi an IP + boot filename; (2) dnsmasq TFTP serves bootcode/start4.elf/config.txt/kernel/initramfs under the Pi's board-serial subdir, auto-created as a symlink to the root the first time the serial appears in the log; (3) an HTTP server on :8080 serves the Alpine diskless initramfs's ROOT filesystem (apks repo, modloop, apkovl) -- without it the initramfs panics 'unable to mount root fs unknown-block(0,0)', since there is no block device over the network and this HTTP server IS the root medium. Same --dhcp-authoritative-required-for-ICS fact as netboot-dnsmasq.conf, and the same served-tree-must-be-world-readable fact already in AGENTS.md's netboot section (Alpine initramfs ships boot/initramfs-rpi mode 600).
