Two reusable SSH/SFTP gotchas found in test/hardware/bisect-1hz-stall.js, general lessons for any future script writing config files to the device over sftp: (1) SFTPv3's rename() onto an EXISTING destination fails with a bare 'Failure' status -- unlike POSIX rename(2), SFTPv3 rename has no atomic-overwrite guarantee, so a target that already exists must be unlinked first (ignore the unlink's own success/failure either way, since the target may not exist on a first-ever run, and the subsequent rename is the real arbiter of success). This is why a first SFTP-write-then-rename call in a fresh connection can fail when later calls in the same connection succeed -- there's no prior successful rename to have already cleared the target. (2) A naive regex checking whether a config directive is actively set (e.g. /disable_core3_lv2\s*=\s*1/) can false-positive-match the SHIPPED REFERENCE COMMENT for that same directive (config/aloop.conf ships '# disable_core3_lv2 = 1' as a commented-out discoverable toggle, documented in AGENTS.md) -- must anchor the match to line-start with no leading '#' to distinguish an active setting from its own commented-out documentation example. NOTE for the coordinator: this script's own header frames a ~30-37ms/~1Hz stall investigation with 'CPU governor and Ableton Link already ruled out this session via direct A/B tests', but AGENTS.md's pinLinkThreadsToControlCore section documents that exact ~30-37ms/1Hz stall class as LATER traced to Link's own peer-discovery threads and fixed via CPU-affinity pinning -- this bisection tool's premise (that Link was ruled out) may be from an earlier, superseded point in that same investigation. Worth the coordinator checking whether this whole script is now dead/historical rather than a live diagnostic tool.
